# Alerts

An alert rule watches one measure of a project's spans or MCP calls and notifies channels when it crosses a
threshold. This guide covers rules, channels, what a receiver gets, and the server settings for outbound calls and
mail. Alerts need the control plane (Postgres) and the master key.

## Rules

A rule has:

- **A measure** of the span rollup: errors, spans, duration or time to first token (as a percentile), cost, or
  tokens. Or, with the source `mcp_ops`, a measure of the MCP rollup: the error rate (typed in percent), errors,
  calls, or the p50, p90 or p99 duration of the calls.
- **For an MCP rule, a side and a capture source.** The rule reads the server side or the client side. With the
  capture source Automatic, each check reads each server from its SDK, else its proxy, else OTLP, so a server
  captured twice is never counted twice; SDK, Proxy or OTLP reads that source only. Calls the caller caused, such
  as invalid parameters, never count, and a server with calls and no error reads 0.
- **Up to two group-by dimensions** (environment, model, span type, level, release; for an MCP rule, server and
  tool). Each combination of values is one series with its own state. A rule tracks at most 50 series, the ones
  nearest to the threshold.
- **A condition**: above, at or above, below, or at or below a threshold, over a window of 1 minute to 24 hours.
- **An interval** of at least 60 seconds. Each check reads the window that ends at the last whole minute at least
  30 seconds before it, which gives the rollup time to receive that minute.
- **A `for` duration**: how long the condition must hold before the series fires. With 0 it fires at the first
  check that breaches.
- **A no-data setting** (**When there is no data**): what a series becomes after it has had no rows for a while
  (**After no data for**, 5 minutes by default). It keeps its state (**Keep the current state**, the default),
  counts as OK (**Treat it as OK**), or goes to `no_data` with one notification (**Notify that there is no data**).
  A series has no rows while none of its spans or calls arrive. For a rule on errors or on a count that fires
  above its threshold, choose **Treat it as OK**: with the default, a series that fired keeps firing while traffic
  has stopped, and is notified again at each repeat. For a rule that fires below its threshold, such as too few
  spans, choose **Notify that there is no data**, since stopped traffic leaves no rows to compare.
- **A repeat interval** (`renotify`, default 4 hours, minimum 5 minutes): how often a series that keeps firing is
  notified again.

| State | Meaning |
|---|---|
| ok | The condition does not hold |
| pending | The condition holds, for less than `for` |
| firing | The condition has held for `for`; channels were notified |
| resolved | The condition stopped holding at the last check; channels were notified |
| no_data | No rows for the no-data time, under the notify setting |

Checks are spread inside the minute by rule, so they do not all run in its first second. After downtime only the
latest check runs; the rule counts the ones that were skipped. A check that cannot read the data leaves the state
as it is, and after five in a row the rule's channels are told once.

Viewers read rules, their history and the preview. Members and admins create and change rules. API keys with the
`read` scope read them; no key changes them.

## Channels

Project admins manage channels, because channels hold secrets. Members see the channels' names and states, so
they can pick them for a rule. Deleting a channel takes it off the rules that named it at their next edit; until
then those rules skip it.

| Kind | What you enter | Secret |
|---|---|---|
| Webhook | A URL. Addresses on your own network and plain `http` work by default | A signing secret, generated by the server and shown once. "Rotate secret" replaces it |
| Slack | An incoming-webhook URL that starts with `https://hooks.slack.com/` | The URL itself: it is stored sealed and only its last characters are shown |
| Email | Up to 20 recipients | None. Needs the `smtp.*` settings below |

"Send test" makes one attempt and reports whether the receiver accepted it, the class of its status and how long
it took. It never shows what the receiver answered. A channel takes 6 tests a minute.

Crucible calls a webhook URL from where it runs. Under Docker Compose, `127.0.0.1` and `localhost` are the Crucible
container itself, so a receiver on your machine at `http://127.0.0.1:<port>` fails the test with "Crucible couldn't
connect to the receiver". Give an address the container can reach: the receiver's container name on the Compose
network, or, with Docker Desktop, `host.docker.internal` for your machine.

A notification that fails is retried after 5 seconds, doubling to 1 hour. After 50 failed deliveries in a row the
channel is turned off and shows the reason. Fix the receiver, send a test, then turn the channel on again: a
series that still fires is notified at its next repeat.

### Verifying a webhook

Each delivery is a `POST` with a JSON body and these headers:

| Header | Value |
|---|---|
| `X-Crucible-Signature` | `t=<unix seconds>,v1=<hex HMAC-SHA256 of "<t>.<body>" under the signing secret>` |
| `X-Crucible-Delivery` | The id of the notification, the same at every retry: use it to drop repeats |
| `X-Crucible-Event` | `alert.firing`, `alert.renotify`, `alert.resolved`, `alert.no_data`, `alert.evaluation_failing` or `alert.test` |

Compute the HMAC over the timestamp, a dot and the raw body, with the whole signing secret (`whsec_...`) as the key,
compare it in constant time, and refuse a timestamp that is too old for your tolerance. In Python:

```python
import hashlib, hmac, time

def verify(secret: str, header: str, body: bytes, tolerance_s: int = 300) -> bool:
    parts = dict(item.split("=", 1) for item in header.split(","))
    t, signature = parts["t"], parts["v1"]
    expected = hmac.new(secret.encode(), f"{t}.".encode() + body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature) and abs(time.time() - int(t)) <= tolerance_s
```

Redirects are not followed: give the receiver's final URL. The body names the event, the rule, the series, its
state, value and threshold, and the evaluation time; a test notification (`alert.test`) says that the channel
works.

## Server settings

Outbound calls follow the server's egress policy: by default any address except cloud metadata addresses, private
networks and plain `http` included; with `egress.mode = strict`, public `https` addresses only, plus the ranges in
`egress.allow_cidrs`. Email channels need the `smtp.*` settings. Both are described, with every setting, in
[alerts and egress](../self-hosting/alerts-and-egress.md). A refused target says which setting changes it.
